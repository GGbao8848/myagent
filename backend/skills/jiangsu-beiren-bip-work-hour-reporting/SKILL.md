# BIP 工时填报

脚本入口：`scripts/report.py`（相对于本 skill 根目录，执行时 `cd` 到 skill 根目录或使用绝对路径）。

> ⚠️ 绝对不要重写或重新创建这些脚本文件，直接 import 使用。
> ⚠️ 所有模式内部已含登录+考勤扫描，不要拆成多步。

## ⚡ 触发规则

当用户提到"报工"/"填报工时"/"提交工时"/"扫描考勤"时，按以下逻辑**立即执行**：

```
用户说"报工"
  ├─ 凭据未就绪（用户未提供过账号密码）
  │     → 发「用户引导」欢迎消息，索取账号密码
  │
  └─ 凭据已就绪（用户已提供账号密码）
        → 🚀 只做两件事（不要发欢迎消息，不要追问，不要查任务列表）：
          1. python report.py -u <user> -p <pass> --scan
          2. python report.py -u <user> -p <pass> --submitted
        → 汇总两条命令的输出，按「分析输出模板」呈现
        → 展示分析报告后，问用户："你想怎么操作？"
          可选项必须包含：报工（单日/批量）、拆分报工、查看报工单详情、删除报工单、撤销审批
        → **自动检测拆分**：如果用户在描述中已给出同日多任务+多工时（如 "前端4h + 测试4h"），
          跳过询问，直接按拆分报工处理，用 --item 逐条提交
        → 用户选了"报工"之后，再追问：工作类别 → 任务/阶段 → 内容
          （此时才运行 --list-phases 查任务列表）
```

> ⚠️ 拿到考勤和报工单数据之前，禁止运行 --list-phases 或追问参数。
> ⚠️ 分析报告展示之前，禁止追问日期、工时、任务、内容等参数。

## 用户引导（仅凭据未就绪时使用）

当用户说"报工"、"填报工时"、"提交工时"等意图时，**仅当凭据未就绪**才发这段引导：

```text
👋 你好！我可以帮你完成 BIP 工时相关的所有操作：

📝 报工流程：
  1️⃣  提供 BIP 账号和密码
  2️⃣  我会自动拉取考勤和报工单，告诉你哪些日期待报工、哪些已报工
  3️⃣  告诉我工作类别（部门工作 / 项目工时 / 销售支持）、任务/阶段、报工内容
  4️⃣  一键提交+审批，支持单日或批量补报

📋 报工单管理：
  • "查看报工单" — 查看已提交报工单及审批状态
  • "删除报工单 RPTxxx" — 删除指定报工单（审批中自动撤销后删除）
  • "撤销报工单 RPTxxx" — 仅撤销审批，不删除

📊 拆分报工（精细化）：
  • "拆分报工 7月10日" — 将一天工时拆分到不同任务
  • 例如：部门工作 skill开发 月结问题处理 6h + 部门工作 skill开发 系统维护 2h + 部门工作 T02会议 课题讨论 2h(加班)

请先提供你的 BIP 账号和密码～
```

## 意图 → 命令映射

| 用户说 | 执行 | 追问条件 |
|---|---|---|
| 只提供凭据，未提"报工"/"扫描" | 自动执行「自动分析流程」（`--scan` + `--submitted`） | 缺凭据 |
| "扫描" / "查看考勤" | 自动执行「自动分析流程」（`--scan` + `--submitted`） | 缺凭据 |
| "报工"（凭据已就绪，未指定参数） | 自动执行「自动分析流程」→ 展示分析结果 → 引导用户选择工作类别、日期、任务、内容 | 缺凭据、工作类别、内容、任务/阶段 |
| "报工" + 部分参数 | 先执行「自动分析流程」展示上下文，再执行报工命令；脚本缺参时列出可选列表并报错退出；agent 收到错误输出后**必须**将列表展示给用户选择，**禁止**自动选取第一条 | 追问所有缺失的必填参数 |
| "批量报工" / "自动报工" | 先执行「自动分析流程」展示待报日期，再执行 `--auto -w <type> --phase-id <id> -c <content>` | 缺类型、任务/阶段或内容 |
| "拆分报工" / "精细化报工" | agent 引导用户列出拆分明细，用 `--item` 逐条传入 | 缺拆分明细 |
| **自动检测拆分**（用户未说关键词，但描述了同日多任务+多工时） | 同上，自动进入拆分报工流程 | — |
| "查询已提交" / "查看报工单" | `--submitted`（单独执行，不走分析流程） | — |
| "查看任务" / "有哪些任务" / "任务列表" | `--list-phases -w <type> [--project-id <pid>]`（单独执行） | 缺工作类别时追问；项目工时/销售支持缺 --project-id 时追问 |
| "删除报工单" / "删掉" + 单号 | `--delete-doc <DocNo>`（单独执行，审批中自动先撤销再删除） | 缺单号时追问 |
| "撤销报工单" / "撤回" + 单号 | `--revoke-doc <DocNo>`（单独执行） | 缺单号时追问 |

> **边界情况**：`--scan` 返回 0 条待报工时 → 告知用户全部已报工，仅展示 C/D/E 选项（查看/删除/撤销报工单）。`--submitted` 返回空 → 报告中标明"无已提交报工单"。两条命令中有一条失败 → 展示已有结果 + 报错信息，不中断流程。

**凭据来源**：用户在对话中提供账号密码，agent 通过 `-u -p` 参数传递给 CLI。

## 自动分析流程（核心）

当用户说"报工"且凭据就绪时，agent **必须先执行此流程**，再根据结果引导用户。

### 触发条件

以下任一场景触发自动分析（agent 自动执行，**无需用户额外指令**）：
- 用户说"报工"/"填报工时"/"提交工时" 且凭据已就绪
- 用户首次提供凭据后（用户在对话中提供了账号密码）
- 用户说"扫描考勤"/"看看考勤"

### 执行步骤

Agent 需**连续执行两条命令**并汇总分析：

```bash
# Step 1: 扫描考勤 → 了解哪些日期待报工/已报工/异常
# 范围：从昨天往前推 30 天，不含当天
python report.py -u <user> -p <pass> --scan

# Step 2: 查询已提交报工单 → 了解审批状态，判断是否可删除/覆盖
python report.py -u <user> -p <pass> --submitted
```

### 分析输出模板

Agent 汇总两条命令的输出，按以下模板呈现给用户：

```text
📊 考勤与报工单分析报告
═══════════════════════════════════

🔴 待报工日期（N 天）：
  [1] 2026-07-02  8h  打卡: 09:00 → 18:00
  [2] 2026-07-01  8h  打卡: 08:55 → 17:50
  ...

🟢 已报工日期（M 天）：
  2026-06-30  8h  DocNo: RPT20260701001  审批中
  ...

🟡 考勤异常（K 天，需手动指定工时）：
  2026-06-28  打卡: 09:30 → 17:00  (工时=0)
  ...

⚪ 无考勤（L 天）：
  2026-06-25  无打卡记录
  ...

📋 报工单概况：
  审批通过: X 条  |  审批中: Y 条  |  已驳回: Z 条

💡 建议：
  → 有 N 天待报工，可单日报工或一键批量报工
  → 批量报工: "批量报工 部门工作 skill开发 日常开发"
  → 单日报工: "报工 7月2日 部门工作 skill开发 日常开发"
```

### 分析后的引导策略

展示分析报告后，**必须**先列出所有可选操作让用户选择，**禁止**直接跳到追问参数。

分析报告后向用户询问：
```text
你想怎么操作？
  A. 📝 报工 — 提交待报工日期（单日或批量）
  B. � 拆分报工 — 一天内按任务/工时精细化拆分提交
  C. 👀 查看报工单 — 查看某条报工单的详细信息
  D. 🗑️ 删除报工单 — 删除指定报工单
  E. ↩️ 撤销审批 — 撤销某条报工单的审批
```

只有用户明确选择 A（报工）后，才进入报工参数引导：

| 分析结果 | 引导方向 |
|---|---|
| 有 1 天待报工 | 直接问：工作类别 → 任务/阶段（此时才执行 `--list-phases`）→ 内容 |
| 有 2+ 天待报工 | 先问"单日还是批量？"→ 单日则追问具体日期 → 然后工作类别 → 任务/阶段 → 内容 |
| 有待报工 + 有考勤异常 | 正常日期按上述处理；异常日期提醒用户需 `--hours` 手动指定 |
| 无待报工 | 告知用户全部已报工，仅展示 C/D/E 选项（查看/删除/撤销报工单） |
| 有已驳回报工单 | 在可选操作中额外提醒"你有 X 条已驳回报工单，可删除后重新报工" |

> ⚠️ `--list-phases` 只在用户选 A 且指定了工作类别后才执行，不要在分析阶段提前运行。
>
> **直接命令路径**：当用户直接说"查看报工单"、"删除报工单 RPTxxx"、"撤销报工单 RPTxxx"、"有哪些任务"时，不经过分析流程，直接执行对应命令。分析流程仅当用户说"报工"/"扫描考勤"/提供凭据时触发。

## 参数

### 必填

| 参数 | 说明 |
|---|---|
| `-w --work-type` | `部门工作` / `项目工时` / `销售支持` |
| `--phase-id` | 任务/阶段 ID 或名称关键词（支持模糊匹配），未指定时列出可选列表 |
| `-c --content` | 报工内容 |
| `--project-id` | 项目号或名称关键词（支持模糊匹配，仅 `部门工作` 不需要） |

### 可选

| 参数 | 默认值 | 说明 |
|---|---|---|
| `-d --date` | 前一天 | `YYYY-MM-DD`（默认取昨天的日期，不包含当天） |
| `--hours` | 考勤自动计算 | 手动覆盖工时。指定后跳过考勤异常检查，在 `--auto` 批量模式下同样生效 |
| `--cost-org` | 项目接口返回 | 成本部门 ID |

### 查询 / 管理模式（不报工）

| 参数 | 说明 |
|---|---|
| `--scan` | 仅扫描最近 30 天考勤（从昨天往前推，不含当天），不提交 |
| `--list-phases` | 查询任务/阶段列表（需 `-w`，可选 `-d`/`--project-id`）。部门工作双渠道：先常用任务再全量列表 |
| `--submitted` | 查询已提交报工单及审批状态 |
| `--audit-status` | 按审批状态筛选（`--submitted` 时可组合使用） |
| `--doc-no` | 按单号筛选已提交报工单 |
| `--delete-doc <DocNo>` | 删除指定单号。审批中(4)自动先撤销再删除；审批通过(8)拒绝删除 |
| `--revoke-doc <DocNo>` | 仅撤销指定单号的审批，不删除。仅对审批中(4)有效 |
| `--auto` | 批量自动报工所有待报工日期。⚠️ 所有日期使用相同的 `--phase-id` 和 `--content`，不同任务需分开报 |
| `--item "类别\|任务\|内容\|标准工时\|加班工时"` | 拆分报工-部门工作（5段），可重复多次 |
| `--item "类别\|项目ID\|任务\|内容\|标准工时\|加班工时"` | 拆分报工-项目类（6段），项目工时/销售支持需指定项目 |

### --item 字段对照

| 工作类别 | 段数 | 格式 |
|----------|------|------|
| 部门工作 | 5 | `部门工作\|任务ID\|报工内容\|标准工时\|加班工时` |
| 项目工时 | 6 | `项目工时\|项目ID\|任务ID\|报工内容\|标准工时\|加班工时` |
| 销售支持 | 6 | `销售支持\|项目ID\|任务ID\|报工内容\|标准工时\|加班工时` |

示例：

```bash
# 部门工作
python report.py -u xxx -p xxx -d <date> \
  --item "部门工作|skill开发|月结问题处理|6|0" \
  --item "部门工作|T02|课题讨论|0|2"

# 项目工时
python report.py -u xxx -p xxx -d <date> \
  --item "项目工时|BRS26139|项目启动|启动会|4|0"
```

> 拆分报工自动校验：标准+加班工时总和可超过考勤值（会警告），吃饭时长自动调整以满足 BIP 校验。

## 模式

| 模式 | 命令模板 |
|---|---|
| 扫描 | `report.py -u xxx -p xxx --scan` |
| 查看任务 | `report.py --list-phases -w <type> [--project-id <pid>]` |
| 单日 | `report.py -u xxx -p xxx -d <date> -w <type> --phase-id <id> -c <content> [--project-id <pid>]` |
| 批量 | `report.py -u xxx -p xxx --auto -w <type> --phase-id <id> -c <content> [--project-id <pid>]` |
| 查询已提交 | `report.py --submitted [--audit-status 4] [--doc-no RPTxxx]` |
| 删除报工单 | `report.py --delete-doc <DocNo>` |
| 拆分报工 | `python report.py -u xxx -p xxx -d <date> --item "部门工作\\|skill开发\\|内容\\|6\\|0" --item "项目工时\\|项目ID\\|任务\\|内容\\|4\\|0"` |
| 撤销审批 | `report.py --revoke-doc <DocNo>` |

## 拆分报工流程

当用户需要对一天工时进行精细化拆分时（如 A 任务 6h、B 任务 2h、C 任务 2h 加班）：

1. Agent 引导用户列出每个拆分项：工作类别、任务/阶段、内容、标准工时、加班工时
2. 用户确认后，Agent 用 **`--item` 标志**逐条传入（格式见上方字段对照表）
3. 执行 `python report.py -u xxx -p xxx -d <date> --item "..." --item "..."`
4. 系统自动：获取考勤 → 解析阶段（支持常用任务→全量列表降级）→ 单次提交多明细 → 审批+改状态

> ⚠️ **禁止用 JSON/管道/文件方式传拆分数据**。统一用 `--item "类别|任务|内容|标准工时|加班工时"`，格式固定，agent 拼字符串即可，零转义风险。

> ⚠️ BIP 限制同一天只能有一条报工记录。拆分报工将多条明细合并为一个 DocNo（多 DetailSeq），不创建多条独立记录。

## 审批状态码

| 状态码 | 含义 | 可删除 | 可撤销 |
|---|---|---|---|
| 1 | 待提交 | ✅ 直接删 | — |
| 2 | 已撤销 | ✅ 直接删 | — |
| 4 | 审批中 | ✅ 自动撤销后删 | ✅ |
| 8 | 审批通过 | ❌ | ❌ |
| 16 | 反审核 | ✅ 直接删 | — |
| 32 | 已驳回 | ✅ 直接删 | — |

## 任务查询双渠道（部门工作）

部门工作任务查询有两个渠道，`--list-phases` 和报工时的 `--phase-id` 匹配均自动按此优先级处理：

| 优先级 | 渠道 | SrcCopied | 说明 |
|---|---|---|---|
| **1 主** | 常用任务 | `GETCANREPORTTASKSLISTS` | 用户已配置/使用过的任务，带预填 CostOrg。有数据则优先用于匹配 |
| **2 保底** | 全量列表 | `TaskList` | 全部可选任务 (T01-T08)。仅在主渠道返回空时启用 |

报工匹配 `--phase-id` 的逻辑：先在主渠道结果中模糊匹配 → 匹配不到则回退到保底列表匹配。

## 销售支持的特殊处理

"销售支持"介于部门工作和项目工时之间：

- **字段映射**：与部门工作一致，使用 `Item`/`ItemName` 字段，按 `isLocked`/`isDeleted` 过滤
- **项目关联**：与项目工时一致，需要 `--project-id` 来查询阶段列表
- `--list-phases` 和报工时均需提供 `--project-id`

## 删除流程

```
1. 查询报工单状态（审批通过(8) → 拒绝删除，流程终止）
2. --delete-doc <DocNo> 直接尝试 PM300300 mode=3 删除
3. 若被拒（DELFAIL），自动执行撤销：
   a. PM300300 mode=8 execmode=UnAudit  → 反审核
   b. PM300302 mode=2 execmode=UnAudit → 更新明细状态
4. 重新尝试 PM300300 mode=3 删除
```

## --scan 输出分类

| 分类 | 含义 | 判断依据 |
|---|---|---|
| 🔴 待报工 | 考勤正常，尚未提交 | `StdHours > 0` 且无 `resultflag="0"` |
| 🟢 已报工 | 已有报工记录 | `resultflag="0"` + `"已有报工记录"` |
| 🟡 考勤异常 | 有打卡但无工时数据 | 有 `OnDateTime` 但 `StdHours == 0` |
| ⚪ 无考勤 | 无打卡记录 | 无 `OnDateTime` |

扫描范围：从昨天往前推 30 天（不含当天）。

## 核心规则

- **凭据就绪后必须先自动分析**：用户说"报工"且凭据已就绪时，agent 必须先执行 `--scan` + `--submitted`，禁止跳过此步骤直接追问参数
- **分析报告出来前不问参数**：日期、工时、任务、内容等必须在分析报告展示之后、用户明确选择"报工"后才问
- **自动检测拆分意图**：用户未说"拆分/精细化"，但描述了同日多个任务+工时（如"7月13日 前端4h + 测试4h"），agent 必须自动识别为拆分报工，用 `--item` 逐条提交。判断依据：① 同一日期 ② ≥2 组不同的「内容+工时」描述 ③ 各组工时之和接近当日考勤总工时
- **绝不替用户猜测参数**：`--phase-id`、`--project-id`、`--content` 等关键参数必须由用户明确指定，禁止自动选取第一条
- **报工内容原样传递**：`--content` / `-c` 的工作内容必须使用用户原话，禁止 agent 自行润色、缩写、改写或补充
- **禁止绕过 CLI 查询**：不要直接调用 `query_phases` / `query_projects` 等函数来替用户预选参数，所有报工操作统一走 `report.py` CLI
- 不猜测任何字段，接口失败立即停止
- `部门工作` → 无需 `--project-id`，内部使用 API 编码 `bm` 查询任务
- `销售支持` → 需要 `--project-id`，内部使用 API 编码 `xs`
- `项目工时` → 需要 `--project-id`，内部使用 API 编码 `xm`
- 阶段/任务只选可报工的（`部门工作`/`销售支持` 按 `isLocked`/`isDeleted` 过滤，`项目工时` 按 `canCheck=Y` 过滤）
- `--project-id` 和 `--phase-id` 均支持模糊匹配：ID 精确匹配 → 名称精确匹配 → 名称包含关键词（忽略大小写）；多匹配时报错要求更精确指定
- 考勤异常（工时=0）→ 报错，要求用户指定 `--hours`（除非已显式指定 `--hours`，则跳过检查）
- 已报工日期 → 禁止重复提交，报错提示先删除原报工单
- **拆分报工** → 单日多任务用 `--item` 一次提交（单 DocNo 多明细），不要逐条独立提交（BIP 不允许同天多条独立记录）
- 审批通过(8) → 不可删除、不可撤销
- 已撤销(2) → 无需再次撤销
- 用户未提供 `--phase-id` 时 → 用 `--list-phases -w <type>` 动态查询，展示给用户选择，禁止使用任何写死的任务 ID
